# 第九十七轮的设计：生成的进度与取消

这一轮改了什么见 [更新记录](../../更新记录.md)。前提和前几轮一样：用户是不懂系统的新手。新建世界、打开世界、重新生成（地形、人文、国家……）、撤销到没存着结果的一步，这些久的步骤以前只有一个转圈和“正在计算…”——不知道到哪一步了、还要多久、能不能不要了。第九十六轮加的“5 秒没回过一条就出现‘停止’”是给卡住用的兜底；这一轮做的是正常的久步骤。

生成的结果逐值不变：金标准、摘要、着色器的哈希、界面的快照、`raster-identity` 一个都没有重录。世界文件的格式没变（`DOC_VERSION` 还是 22），IndexedDB 的库还是第 8 版；localStorage 多一项 `map2.progress`（各类请求上一次各步用了多久，丢了没关系）。没有动 `src/render/`。

## 以前是什么样（动手前核对过的）

- 流水线（`core/engine-recompute.ts`）早就是分阶段的（一个生成器，每算完一个阶段 `yield` 一次），但只有确切预览用它在阶段之间停；执行、撤销、重做都是一口气走完（`drain`）。
- 生成人文（`core/human/generate.ts`）是命令里面的一个循环（`for (const stage of STAGES) stage.run(ctx)`），整个在 `applyCommand` 里同步做完。
- 新建一个 4 万格、带人文的世界，在这台机器的 Node 里约 2.6 秒，整个星球（6.26 万格）约 4.3 秒；各步占多少见下面“默认的各步耗时”。最大的一块不在流水线里，是 `set_worldgen` 这条命令自己（造陆地：重新采样整个生成器，连同先加进世界的内容，地区 0.7 秒、星球 1.2 秒）。
- 开着一个世界时新建、打开别的世界，`EngineHost.send` 在**开始时**就把原来的计算 Worker 换掉了（一个 Worker 只装一个世界：脚本不能看到别的世界）。所以新建到一半不要了，原来的世界只在主线程的命令记录里，要回去只有重新打开它。
- 计算 Worker 在同步的计算里收不到主线程的消息（没有 SharedArrayBuffer：页面不是跨源隔离的，Worker 还是从 data: 地址开的）。要听到“请停下”，只能在阶段之间让出线程。

## 1. 回报到哪一步了

### core 里的钩子（`core/progress.ts`）

和脚本的看门狗（`script.ts` 的 `setScriptHost`）一样是进程里的一个钩子：`setStageSink(f)`、`reportStage(步名, 第几步, 共几步)`。没接时 `reportStage` 只是一次判空。说的地方都在步的边界上，不在循环里：

| 哪里 | 说什么 | 一次几条 |
| --- | --- | --- |
| 流水线 `recomputeDerived` | `elevation`、`climate`、`water`（水文、河的类型、植被的第一遍；连同修湖底、查冲突）、`solve`（有“自然融入”的设定时）、`habitat`（人文的几层）、`features`（认地物、起名） | 3–6 |
| 生成人文 `generateHumanSteps` | `human.cultures`、`human.population`、`human.countries`、`human.claims`、`human.blocs`、`human.capitals`、`human.country-mix`，写了城市时再一条 `settlements` | 7–8 |
| `set_worldgen` | `terrain`（造陆地和海） | 1 |
| `generate_provinces`、`regenerate_provinces` | `provinces` | 1 |
| `generate_settlements`、`regenerate_settlements` | `settlements` | 1 |

只重算名字、只重算人文几层的那条短路（`Dirty.Names` / `Dirty.Human`）不说。“共几步”在每一串开头就算好（流水线的 `stageCount`：和下面两个 `if` 同一个条件）。

**只说，不改任何计算**：`core/progress.test.ts` 把同一串操作（造陆地、生成人文带国家和城市、划省份、画陆地、改冷暖、批量里重新生成人文、重新生成国家、撤销两次、重做、换一个、整份重放）在接了钩子和没接钩子的两个引擎上各做一遍，每一步之后的世界摘要（`core/digest.ts` 的 `worldDigest`：原因、推导含人文的几层、小数据）、历史、世界文件的字都逐位相同。

### 从 Worker 到主线程（沿用脚本那条消息的路）

- `src/worker.ts` 接上钩子：带提示的一步（新建、打开、执行、撤销、重做、换一个）在做的时候，每说一声就给主线程发一条 `{kind:'stage', req, step, k, n}`（`protocol.ts` 的 `StagePing`，和 `ScriptPing` 并排；`req` 是那个请求的编号——不叫 `id`：带 `id` 的只有回复，头一版叫 `id` 时 `src/worker.test.ts` 里“按 id 找回复”的那一句把它当成了回复，整个文件没过，才改的）。预览、缩略图、整理的计划、写检查点时的重算、空闲预热不发。
- Worker 自己另说三样：`mesh`（建网格之前）、`restore`（从检查点恢复之前）、`replay`（重放命令：`Engine.fromDoc` 的 `onStep` 每条命令之后说“第几条 / 共几条”，最多每 100 毫秒一条）。重放期间里面的小步（某条命令要先算推导、生成人文的各步）标上 `inner`：只当名字看，数第几步看 `replay` 的那几条；最后一次重算是照常的几步。
- 主线程这边照脚本那一条的规矩：`sandbox.ts` 的 `readWorkerMessage` 先检查（整数的编号、名字截到 40 个字、第几步不超过共几步），`EngineHost` 只把还在等的请求的交给界面（`HostEvents.stage(ping, 那个请求)`）；恢复世界时自己发的那一次打开也说。
- 主线程自己加最后一步 `show`：新建、打开的回复到了，还在等网格、换上快照。

## 2. 进度条画多长（`src/progress.ts`，纯规则）

按时间算，按量到的各步耗时加权：

> 已经过去的时间 ÷（已经过去的时间 + 这一步还要多久 + 后面几步要多久）

- **“要多久”从哪来**：这一类请求（`jobKey`：做的是什么——新建按各条命令、执行按命令的种类、批量按最后一条——哪种地图、多少格）**上一次真实走过的各步和各用了多久**（`ProgressBook`，存在 localStorage 的 `map2.progress`，最多 24 类，最久没用的先丢；做了半秒以上、照常做完的才记，取消的、出错的不记）。没有时用一份默认的（下一节）。
- **不骗人**：走完的几步用的是真实的耗时，估的只有剩下的，每到一步的边界按真实的重新算一次；一步里面按时间往前走，最多走到这一步估的九成，之后**停着等它真的做完**——不会自己走到头；重放命令按数出来的快慢算（做了 50 条用了 500 毫秒，200 条就是 2 秒），不靠估；做完之前最多画到 99%。
- **不倒退**：算出来比画着的小（估多了、半路多出没料到的步）就停着不动，等真实的进度追上来。期望里中间没走的几步（只从气候算起的重算没有“高程”）跳过。
- 一条进度条是“连续”的：界面每 0.1 秒取一次，CSS 再匀着走 0.15 秒。

### 多久才显示：1 秒（`SHOW_AFTER_MS`）

量到的编辑里最慢的一步是 0.6 秒上下（一块地区描河 560–640 毫秒，第九十五轮 `bench-median` 的数），其余几十到三四百毫秒。1 秒是它的一倍半以上：平常的每一笔都不闪进度条，照旧只是“正在计算…”；而 1 秒也是人觉得“它在忙”而不是“点了没反应”的界线，再晚就是盯着转圈干等。新建、打开、重新生成都在一秒以上。

**刚过 1 秒就做完的一步**会让进度条闪一下——冒烟里就量到了：4 万格的地区上画一笔陆地，在无头 Chrome（软件渲染，画面占着 CPU）里连同画面的卡顿是 0.9–1.3 秒，进度条露了一帧到 0.3 秒。所以加了一条（`state/progress.ts` 的 `ALMOST`）：到 1 秒时**估着已经过了六成**的（按上一次真实的耗时，或者默认的比例），再等到估计做完的时候（多留 0.1 秒，最多再等 0.5 秒）还没好才显示。也就是：估着还要很久的一步 1 秒就显示，估着快好的一步最晚 1.5 秒。阈值边上总会有闪一下的（估不准的、头一回做的），没有再加“出现了就至少显示半秒”这样的规矩——那是让它看起来不闪。

按“**正在算的这一步**做了多久”算，不按“忙了多久”（和 `stall.ts` 的规矩一样）：连着画十秒、每一笔都按时算完的不出现；排在后面的一步从它轮到的时候算起。接线在 `src/state/progress.ts`：`worker-host.ts` 的 `call` 发带提示的请求时登记（`jobQueued`）、做完时（`jobDone`），正在算的换了一个就重新挂一个 1 秒的定时器；到点了 `progressView` 才有值，之后每 0.1 秒更新。**短的一步不建任何东西**（估算用的轨迹在第一条 stage 消息到时、或者该显示时才建）。

### 默认的各步耗时（`src/progress-defaults.ts`）

出处：`node --import tsx tools/progress-weights.ts --runs 5`（一块地区 4 万格）和 `--globe --runs 5`（类地星球 6.26 万格）——照新建向导的顺序新建一个带人文的世界（建网格 → 加内容、造陆地 → 生成人文、国家、城市 → 划省份），接上钩子，记每一步从开头到下一步开头用了多久，各开一个进程跑五次取中位数（毫秒，这台 Apple M2 上的 Node）：

| 步 | 一块地区 | 整个星球 |
| --- | ---: | ---: |
| mesh 建网格 | 286 | 325 |
| terrain 造陆地和海（连同加内容） | 681 | 1174 |
| elevation | 279 | 459 |
| climate | 315 | 611 |
| water | 111 | 173 |
| habitat | 29 | 48 |
| features | 149 | 266 |
| human.cultures | 141 | 271 |
| human.population | 100 | 151 |
| human.countries | 131 | 202 |
| human.claims / blocs / capitals / country-mix | 10 / 3 / 16 / 21 | 19 / 4 / 21 / 35 |
| settlements（连同之后重算人文的几层、起名） | 201 | 359 |
| provinces | 101 | 148 |

只用它们之间的比例，不当成“要几秒”给用户看；别的格数按格数折算。量的时候机器不闲，同一步五次之间差到一倍（原始的五次在草稿目录的 `weights-region-5.txt`、`weights-globe-5.txt`）；头一回跑三次时星球的 `human.countries` 有一次是 41 秒（另两次 173、174 毫秒，同样的种子、确定的计算——是机器停顿，不是那一步真的慢）。`solve`、`restore`、`replay`、`show` 四项那个工具量不到，是估的（文件里标着“没量”）。做过一次以后就用那一次真实的了，默认的只管第一次。

## 3. 取消

### 两条路都用，界面上是一个按钮

| | 轻的（这一轮加的） | 重的（第九十六轮的 `stopAny`） |
| --- | --- | --- |
| 做法 | 请计算 Worker 在下一个阶段的边界上自己停下，引擎把世界退回这一步之前 | 结束这个 Worker，用主线程的命令记录另开一个、重新打开世界 |
| 多快 | 最多等正在做的那一小步做完 | 马上停；但恢复要重新打开世界（有检查点时快，没有时重放全部命令，大世界慢） |
| 重做记录 | 还在 | 没了（说“重做记录已清空”） |
| 用在 | 改动世界的一步：执行、撤销、重做、换一个 | 新建、打开；计算程序已经 5 秒没有任何消息；点了轻的以后才沉默满 5 秒的 |

`state/worker-host.ts` 的 `stopBusy()`（按钮只调它）：正在新建、打开，或者已经没动静（`stalled`），或者还没有世界 → 重的；不然 → 轻的（`EngineHost.cancelEdits`），并把 `cancelling` 设上（界面写“正在取消…”，按钮按不了）；之后 `Stall` 一报“5 秒没动静”就自动改用重的。

**为什么新建、打开不用轻的**：原来的 Worker 在开始时已经换掉了。就算让新的 Worker 在阶段之间停下，原来的世界还是要在另一个 Worker 里重新打开（新的那个跑过新世界的脚本，不能再装别的世界）——轻的在这里一点不省，重的反而马上就停。代价是回到原来的世界要等一次重新打开（这一阵也有进度条，没有“取消”）；要省掉它得让原来的 Worker 留到新世界建成才换，两个引擎同时在（星球上多一倍内存），这一轮没有做。

### 轻的那一种怎么做到“不留半截”

**取消 = 在一个停着的地方往分阶段的计算里抛一个错**。引擎本来就保证“整步要么生效要么不生效：命令做不了、重算中途出错，都回到执行前的样子（原因、推导、历史、重做记录、状态编号都与执行前相同）”——第三批就有，有测试。取消没有另写一套回退，走的就是这条路：

- `Engine.exec` / `undo` / `redo` / `replaceLast` 改成 `execSteps` 等几个生成器再一口气走完（`exec(cmd) = drain(execSteps(cmd))`）。函数体原样，只是里面的 `this.update()` 换成 `yield* this.updateSteps()`、`this.applyOnly()` 换成 `yield* this.applySteps()`；`try / catch` 一个没动。
- `applyCommand` 多了一个分阶段的孪生 `applyCommandSteps`。两个都只是壳：原来那一个函数的身子原样拆成四段普通函数——`beginApply`（校验、记下之前的样子）、`settleApply`（命令做完之后的国名、城市、记着的名字与整理）、`failApply`（原来 `catch` 里的原样放回）、`finishApply`（撤销记录、内容的增减），先后不变。同步的 `applyCommand`（重放、预览、`Engine.applyOnly` 走的）**不经过生成器**；`Engine.applyOnly` 的后半段也提成 `noteApplied`，同步的和分阶段的共用。头一版是 `applyCommand = drain(applyCommandSteps)`、整个身子在生成器里——`bench-median -- --library` 两遍都把 libContent、libNoop 标成 +8–9%（1.12 → 1.22 毫秒），所以改成了现在这样（数见“量到的数”）。
- 只有生成、重新生成人文和国家的命令（单独一条或者在批量里）中间会停：那三段从 `runHumanOp` 原样搬进 `runHumanGenSteps`，`generateHuman` 的循环每做完一步 `yield` 一次。别的命令照旧一步走完（`stepped(cmd)` 为假时走的还是原来的 `run`）。停在生成人文的两步之间被抛进一个错，落进原有的那段“原样放回”（`failApply`），这一步根本没进历史。
- 计算 Worker 里 `worker-steps.ts` 的 `runSteps` 走这些生成器：**一步开始后的半秒（`YIELD_AFTER_MS`）以内一次都不让出线程**，和以前一口气走完是同一条同步的路；过了半秒，每到一个边界让出一次（这时收得到主线程的 `cancel`），回来发现不要了就 `steps.throw(new Stopped())`。按钮 1 秒才出现，Worker 半秒起就在每个边界上听着。
- 让出用一条 MessageChannel 给自己发消息，不用 `setTimeout(0)`（连着几次以后浏览器把它拖到 4 毫秒一次，二十来个边界就是近 0.1 秒）。
- **让出期间别的请求插不进来**：Worker 的请求本来就一个接一个处理（`queue`），这一个没回复后面的都排着；空闲预热在有请求时不跑；补写检查点也走 `queue`。让出时能进来的只有两种立即回复、不碰引擎的消息：`cancelPreview`（原来就有）和这一轮的 `cancel`。
- `cancel` 带着 `upTo`（主线程发出的最后一个请求的编号）：编号不超过它的改动，正在算的在下一个边界停下，**排着还没算的不算了**（画了一半队的几笔一起不要），都回 `{ok:false, soft:true}`；取消之后才发的照常算。
- Worker 说的 `soft` 只有主线程确实要它取消过这一个请求、而且那是改动世界的一步时才作数（`EngineHost.receive`）：脚本伪造不出“被取消了”，伪造的只当一条普通的出错。

`core/progress.test.ts`：改冷暖、重新造陆地、重新生成人文（单独一条、在批量里）、重新生成国家，每一步的**每一个**停的地方各抛一次错——世界的摘要、历史、能不能撤销 / 重做、每一步的编号、状态编号、世界文件的字都和这一步之前相同；之后再做同一步，和从来没取消过的一样。撤销、撤销两步、重做、换一个，存着推导和没存推导两种，同样每一个停的地方抛一次。`src/worker-progress.test.ts` 拿真的 `worker.ts`（假的 `self`）做：计算正做到“分人口”时塞进一条 `cancel` → 停在它之后的那个边界、回 `soft`、世界文件不变、重做照常、再做同一步和本地照样做的逐位相同。

### “多久没回过一条”和进度消息的关系

**进度消息算“回过一条”**：它和回复一样是计算程序还活着、在往下算的证据（`worker-host.ts` 里 stage 一到就 `stall.progress()`）。所以：

- `stalled`（5 秒没有任何消息）的意思收窄成“**卡在一个阶段里**”——一步一步往下说着的久步骤不算卡住，哪怕它一共要一分钟；
- 它不再管按钮出不出现（久的一步 1 秒后就有进度条和“取消”），管的是取消用哪一种：没动静的听不到“请停下”，只能结束它；
- 轻的取消退回时如果要重算（撤销到一半取消：那一步放回去以后从头重算一遍），重算的各步照样在说，不会被当成没动静而再结束一次。

一个阶段正常就要 5 秒以上的大世界上，点了取消会走重的那条（和第九十六轮一样：等不到它，就结束它）。

### 取消以后说的话

| 情况 | 说什么 | 世界 |
| --- | --- | --- |
| 改动世界的一步，它自己停下了 | 已取消，世界回到了这一步之前 | 原样；重做记录还在（所以不提） |
| 同上，但结束了它（没动静） | 已取消，世界回到了这一步之前（撤销过几步时加“。重做记录已清空”） | 用命令记录恢复 |
| 新建、打开到一半，原来有世界 | 已取消，回到了原来的世界（同上加一句） | 重新打开原来的世界 |
| 启动时正在打开上次的世界 | 已取消。上次的世界还留在浏览器里 | 进向导，那一份留着 |
| 向导里新建，原来没有世界 | 已取消 | 留在向导 |
| 点的那一刻这一步正好做完了 | 不说“已取消”：照常是这一步的那一句和“撤销” | 这一步做了 |

### 一个按钮、一种说法

第九十六轮的“停止”并成了“取消”：同一个 `button.busy-stop`，同一个 `stopBusy()`，不管是算得久还是卡住了。说法从“已停止，回到了这一步之前”改成“已取消，世界回到了这一步之前”（`sandbox.ts` 的 `STOPPED_BACK`、`crash-text.ts` 的 `STOP_TEXT`，[ui-design.md](../ui-design.md) 的叫法表跟着改了）。选“取消”不选“停止”：进度条旁的按钮人人认得是“取消”（导出的进度条旁本来就是它），而且它的意思正是“当作没点过”——“停止”听着像停在半路（第九十六轮的文档还专门写了一句“停下不是暂停”）。

三处用的是同一个部件 `shell/BusyLine.tsx`（转圈 + 一句话；久了换成 步名 + 进度条 + 取消）：顶上的提示条、启动时中间“正在打开世界…”那一块、新建向导底下。**页面上任何时候只有一个“取消”**：向导开着时顶上的提示条只留转圈和那一句（进度和按钮在向导里）。正在恢复世界时有进度、没有“取消”（那时再停只会再恢复一次）。

**脚本的“停止”没有并**：一段脚本算了 1.5 秒以上时顶上是“正在运行‘X’的脚本… 停止”，停的是那段脚本（它 4 秒没动静也会自己停），说的是“已停止‘X’的脚本”。它出现时占着提示条，不会和“取消”同时出现。但有一处跟着改了：正在新建、打开时点“取消”，哪怕那一刻正好有脚本在跑，也是不要这个世界了——以前（第九十六轮）这一下会被当成“停下脚本”，换安全模式把那个世界接着打开。

## 4. 顺手改的

- `state/open.ts`：新建、打开没成（出错、被取消）时不再等它的网格建好才算结束——以前取消了新建，提示还要挂着等一张用不上的网格。
- `core/engine.ts` 加之前先拆（793 行）：一步做完之后的三样整理（名字跟着地方走、湖与陆地省份、人口的修补）原样搬到 `core/engine-fixes.ts`，`Engine` 里同名的方法只转过去。现在 762 行。
- `drain` 从 `engine-helpers.ts` 挪到 `progress.ts`（生成人文、命令也要用，它们不该引用引擎的小工具），原处照旧导出。
- 新建向导开着时，顶上的提示条在向导后面、看不到（以前就是）。取消以后的那一句、没能生成的原因现在在向导底下也写一遍（`.wizard-note`）；向导里“正在生成…”那几个字在进度那一行出来以后不再重复。

## 取舍

- **新建、打开的取消是重的**（见上）：回到原来的世界要重新打开一遍。
- **取消要等到下一个边界**：最大的一块（造陆地，星球上一秒多）中间停不了；撤销、重做的回退是“把那一步放回去、从头重算”（引擎原有的出错路径，稳妥但不快）——取消一次撤销可能比等它做完还久。没有为取消另写更快的回退：那要动“推导写了一半能不能信”的判断，不值得冒逐值不变的险。
- **点了取消、这一步却做完了**：不撤回它（没有偷偷替用户撤销），照常显示这一步的结果和“撤销”。
- **进度条第一次是按默认的比例画的**：默认的是在一台机器上量的，别的机器、浏览器里比例会偏；偏了的表现是某一步上停一会儿、或者往前跳一截，不会倒退、不会假装做完。
- **重放命令按条数算**：每条命令花的时间差得很远（一笔画和一次生成人文），条子走得不匀；它说的是“第几步 / 共几步”，是真的。
- **1 秒以内不显示**，哪怕这一步其实是久的：第一秒看到的还是原来的转圈。
- **没有“还要几秒”**：只有比例。估的时间在不同机器上不准，说出来就是骗人。

## 没做的、要知道的

- **“造陆地和海”是一整块**（`set_worldgen` 这条命令自己：重新采样整个生成器）：中间没有边界。进度条在这一步上只按时间走（估的九成处停着等），取消要等它做完——类地星球一秒多；最大的星球（13.9 万格）没量。要把它拆开得动 `terrain.ts` / `planet-gen.ts` 的采样，这一轮没有做。
- **流水线最后两小步之间没有能停的地方**：“宜居度”“起地名”之前最后一次停是在水文与植被那一遍之后（认地物只有改了海陆时中间多停一次）。这时点“取消”，这一步就做完了（照常显示结果和“撤销”，不说“已取消”）。没有在流水线里加停的地方：确切预览走的是同一个生成器，每多停一处它就多让出一次线程。
- **撤销、重做的取消不快**：回退是引擎原有的出错路径——把那一步放回去、从高程起重算一遍（同步的，这期间取消不了，进度照样在说）。
- **新建、打开到一半取消要把原来的世界重新打开一遍**（见第 3 节）。有检查点（打包好的程序、最近写过）时快，没有时重放全部命令。
- **等检查点的那一段没有步名**：打开世界时计算 Worker 先等存储 Worker 发来检查点（最多 5 秒），这期间还没说过哪一步，界面上是“正在打开世界…”和停在 0 的进度条。从检查点恢复之后对齐命令的那一段（撤掉多的、补上少的）是同步的，中间不说。
- **带提示但不是改动世界的请求**（整理这张地图的计划 `planTidy`）：取消是重的那一种。
- **导出**没有动（它本来就有自己的百分比和“取消”）。**我的库**的写入、读文件这些不经过计算程序的久步骤没有进度。
- **脚本的“停止”没有并进“取消”**（见第 3 节）。
- **1 秒、半秒**是按这台机器上量到的编辑耗时定的，没有在慢机器、最大的星球上量过“平常的一笔要多久”。
- **默认的各步耗时**只在这一台机器的 Node 里量过；`solve`、`restore`、`replay`、`show` 四项是估的。
- **计算 Worker 发一条 stage 消息的代价**只在 Node 的 `worker_threads` 里量了（见“量到的数”），没有在浏览器里单独量。
- **`map2.progress` 写不了**（隐私模式、存储禁用）时只在这次打开页面期间记着，每次重新打开页面第一次都按默认的比例画。
- **向导里**顶上的提示条被向导挡着（以前就是）：这一轮只是把那一句在向导底下也写一遍（`.wizard-note`），没有改提示条和弹窗谁盖谁。
- **动手时发现、没有改的一件事**（基线 `695a12c` 上就这样，和这一轮无关）：一份“新建（加内容 + 造陆地）→ 加时代 → 生成人文 → 划省份”的世界文件，用 `Engine.fromDoc` 重放以后再 `toDoc()`，第一条命令里记的省名少了两个（2000 格、种子 4 的那个世界里是 136、424 两个省）。世界的数组没有去比。复现的小脚本在草稿目录的 `replay-doc.mts`（对基线的拷贝和现在的代码各跑一次，输出相同）。

- **没有用眼睛看过的界面**：正在恢复世界时的进度条（没有“取消”的那种；冒烟里读到了它的字和“没有取消”，没截图）；“正在重做第 k / n 步…”（打开一个没有检查点、要重放的世界——冒烟里的世界都只有几步，没走到 1 秒；字和数在测试里）；顶上的提示条里步名一步一步换的样子（冒烟截的那张是计算卡着的，进度停在 0；步名在换是读出来的）；两条提示叠着（“正在恢复世界…”下面一条“已取消，回到了原来的世界”——读到了，没截）；向导底下的那一句 `.wizard-note`（最后才加的，没截到）；900 px 以下的窄窗口里那一行会不会挤；Firefox、Safari；真的显卡上的 Chrome（无头的是软件渲染，画面占着 CPU，时间都偏长——4 万格画一笔在真的浏览器里会不会露出进度条，没法在这里量）。
- **没有在应用管的预览里看**（任务书不让碰 5191 / 5196）：上面这些只在 `npm run smoke` 的无头 Chrome 里走过。
