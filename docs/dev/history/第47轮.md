# 第四十七轮的设计

这一轮改了什么见 [更新记录](../../更新记录.md)；现在的文件见 [开发说明](../../开发说明.md) 与 docs/dev/ 下的各篇。

为什么做：后面的轮次让新世界带上一整个库，空世界的 `small` 从约 27 KB 涨到三百多 KB（这一轮量到带中世纪库的世界 378 KB，其中 `content` 308 KB，22 种地名风格就占 197 KB）。以前每条命令把它序列化两次，撤销解析一次，每步的撤销记录留一整份，每份快照结构化克隆一遍。原来的测速用没有时代的世界，看不到这些。结果逐值不变，金标准一个没重录。

## 带库的测速

`tools/bench.ts --library`（`node tools/bench-median.mjs 5 --against <提交> -- --library`）：新建之后照常用 `packImportCommands` 导入中世纪的包（不生成人文，地图不变），加工步骤与一块地区、星球的完全相同；最后另计不重算推导的几步，这里几乎只有小数据的开销，各 41 次取中位数，两位小数：

- `libEdit`、`libUndo`、`libRedo`：换画风（`set_map_style`）与它的撤销、重做；
- `libContent`、`libContentUndo`：改一项内容（`set_content`）与它的撤销；`libNoop`：改成一模一样的；
- `libPost`：发给主线程的小数据（结构化克隆一遍）；`undoKB`：最后一步的撤销记录（千字）。

`--against` 把现在的 `bench.ts` 复制到旧提交上，所以旧提交不用认识这个参数；只用 `set_map_style`（第三十七轮起有），第三十七轮之前的提交跑不了这一段。`libPost` 用 `postedSmall`，旧提交上没有时量整份。bench 在主线程这一边，可以引内置的数据；计算 Worker 仍然不打包（`src/worker-imports.test.ts` 查着，`core/small-copy.ts`、`src/content-post.ts` 都不引 `core/packs/`）。

## 内容不可变，按引用共用

`core/small-copy.ts`：

- **`copySmall`**：`{ small: 除内容以外的 JSON, content: 引用 }`。JSON 里内容的位置上留占位 `0`（`{ ...small, content: 0 }`，赋给已有的键不改先后），没有内容时没有这个键。
- **`restoreSmall`**：解析之后把引用赋回占位，键的先后与以前解析整段 JSON 一样，世界文件、摘要逐字节不变。
- **`sameAsCopy`**：等于比两段完整的 JSON。先比不带内容的那段，再逐层比内容（种类 ▸ 项），同一个对象不序列化，换过的项才序列化。键的先后算数，`undefined` 不算键——都和序列化以后比一样。所以 `set_content` 改成一模一样的、`order_content` 排成原样还是“没有变化”，也不用把 197 KB 的风格序列化一遍。
- **`cloneSmall`**：预览的副本、`Engine.clone`、省份预览：克隆不带内容的部分，内容共用。

`UndoRecord` 继承 `SmallCopy`（`small`、`content`）。`applyCommand`、`revert`、`Engine.carryNames`、`replaceLast` 都走它。什么都没改的命令把内容换回执行前的对象（一字不差）：不然 `setContent` 换出来的新对象会让之后的共用、缓存白白错过一次。

`contentSnapshot` / `contentDiff`：放在 `small.content` 的种类只记那一种的对象，前后是同一个对象时这一种不比（以前每条命令把全部内容排成 Map）；以前的种类（生态、河湖、岛、场）当时就列好，它们的数组可能就地改。

检查点（`toCheckpoint`）发给存储 Worker 是一次结构化克隆，同一条消息里相同的引用克隆以后还是同一个对象（`IndexedDB` 的 put 也一样），所以几百步只存一份内容，恢复之后也是共用的。`build` 不同的检查点本来就不用，不用管旧格式；世界文件的格式没变，`DOC_VERSION` 不动。

## 查过：谁在写内容

内容不可变是这一轮安全的前提。两种办法一起查：

1. **读代码**：`small.content` 的写法只有 `setContent`、`orderContent`（`core/commands/features.ts`）、`pruneHumanContent`、`dropBroughtContent`（`core/human/prune.ts`），都是复制一层再整个换掉；`tidy_content` 走 `set_content` 的路；`setOrigin`、`tidyOrigins` 写的是 `small.origin`，也是换掉。界面（`src/ui/`）里编辑内容的表单都改自己的副本，再发 `set_content`。没有发现就地改的地方，所以没有要修的。
2. **冻住跑一遍**：临时在 `applyCommand` 前后把 `small.content` 深冻结（模块是严格模式，就地改会抛错），跑全部测试：1760 个通过，另外 2 个是机器忙时的超时（`core/sizing`、`tools/realism`，这两个在冻住的那一遍里没有跑完）。这个补丁没有留下；留下的是 `core/content-share.test.ts` 里的一段：内容冻住，走一遍改内容、排先后、生成人文（生成后清理）、重新生成国家和城市、去掉、整理、撤销、重做、预览。

主线程上按内容对象认的缓存（`worldCultures` 等的列表、`worldTiers`、`cityTable`、`settleLists`、`statsOf`、`tupleCodes`、画风的 uniform、地名风格的表）也看过：每一个的结果都只取决于它的键。Worker 这边改小数据时内容对象本来就不换，所以它们不会靠“内容对象每次都新”才对；`statsOf`、`settleLists` 的键里还有每份快照都新的别的小数据，行为和以前一样。

## 发给主线程

`src/content-post.ts`：`ContentSender`（Worker）记着上一次发的内容对象，没换时快照里是占位 + 编号（`contentRev`、`sameContent`）；`ContentHolder`（主线程）记着上一次收到的，补上同一个对象。主线程的 `handle`、`engineRestored` 都先过它；补不上（手上的不是那一份）时和只带变了的数组一样要一份完整的快照。编号前面是 Worker 的 `performance.timeOrigin`：换了 Worker、第一份又没用上时也不会碰巧对上上一个世界。

预览世界的回复（`postedPatch`）：内容与当前世界是同一个对象时不带，主线程补上手上的那一份。`previewReply` 本来就只用同一状态的预览（`stateId`），所以手上的就是那一份，不用编号。

没做的：改了内容时还是整份发（不按种类发）。内容编辑不常有，再省要多一层键的先后的记法。撤销一步内容也会再发一次。

## 撤销的内存

`done` 仍然没有上限（那是行为，不动）。每步的撤销记录从整份（380 千字）变成不是内容的部分（72 千字，这个 4 万格的世界主要是省份）。一个字符 1–2 字节，按两字节估，带库的世界一千步以前约 760 MB 的字符串，现在约 144 MB（估算，没有量堆）。省份那一段没有再压：它是就地改的（`p.name = name`），要共用得先把写法都改了。

## 量到的数

都与 `b22cd29` 对照。一开始负载 4–23 量过一遍，噪音太大（见下），后来在负载 3–7 重量，下面的数都是这一遍的。

带库的世界（`node tools/bench-median.mjs 5 --against b22cd29 -- --library`，五次中位数，4 万格，`small` 378 KB、`content` 308 KB；负载高时那一遍的 `lib*` 几乎一样）：

| 步骤 | 旧 | 新 |
|---|---:|---:|
| 编辑（`libEdit`，不重算） | 6.98 ms | 1.25 ms |
| 撤销（`libUndo`） | 6.32 ms | 2.60 ms |
| 重做（`libRedo`） | 6.99 ms | 1.24 ms |
| 改一项内容（`libContent`） | 6.94 ms | 1.22 ms |
| 撤销它（`libContentUndo`） | 6.55 ms | 2.64 ms |
| 没有变化（`libNoop`） | 7.04 ms | 1.24 ms |
| 发给主线程的小数据（`libPost`） | 7.31 ms | 0.94 ms |
| 一步的撤销记录（`undoKB`） | 380 千字 | 72 千字 |
| 撤销（换回存着的推导，`undo2`–`undo5`） | 7–8 ms | 3–4 ms |
| 从检查点恢复（`openCheckpoint`） | 64 ms | 58 ms |

这一遍另外报了 `rivers` +8%、`erod` +14%、`rerollFjord` +10%（高负载那一遍报的是 `relief`、`erod`、`paintLand`，每遍不一样）。`erod` 多出来的 33 ms 里，高程 +22、气候 +17，`apply`（命令本身，这一轮动的就是它）+4；`rerollFjord` 的 `apply` −2，涨的是高程。各步 `apply` 加起来 1657 → 1547 ms。

普通的世界。`bench-median --against` 总是旧的先跑，这里量出来有偏差，所以另外用一个临时脚本旧、新轮流先跑（ABBA，同样的 `bench.ts`）：

- **一块地区**（`--`，8 轮）：中位数没有超过 +5% 的（最高 `latShift` +4%，`rivers` −5%，`redo` −4%）；每步的最小值也都在 +5% 以内（`latShift` +5%，`erod` +4%，`hotRelief` +4%）。`openCheckpoint` 最小值 9 → 15 ms、中位数 18 → 18 ms，不是加工的步骤。
- **星球**（`-- --globe`，6 轮）：**中位数不可信**：这一遍机器上另有 Chrome 在跑（负载升到约 7），两边都有单次慢几倍的（`rivers` 8161 ms、`redo` 4665 ms、`island` 3078 ms）。中位数上 `erod` +26%、`lake` +29%、`rivers` +17%、`humidity` +15%、`relief` +12%，同时 `reroll` −12%、`tempBrush` −16%、`hotRelief` −27%。每步的最小值：加工各步都在 +3% 以内（`erod`、`latShift` +3%，`relief`、`lake` +0%，`rivers` +1%）；不是加工的 `warmupLongestChunk` +10%。

`bench-median` 那一遍：一块地区（负载 4）报了 `rivers` +12%、`lake` +6%、`redo` +18%，换成 ABBA 以后都没有了。

**同一个提交对照自己**（`--against HEAD`，代码一字不差，负载高时量的）：星球 −50% 到 +57%，一块地区 −36% 到 +14%。所以星球这一项只能说最小值没有变慢；要更确切得在机器空闲时再量一次。

`worldRivers`、高程、气候这几段读不到内容（`riversKey` 只看数组和几个小数据的字段），动的只有 `applyCommand`、`revert`、副本的克隆。

## 没有确认的

- 真的界面没有开过（这一轮不碰开发服务器），主线程补内容、预览补内容只在 `src/content-post.test.ts`、`src/worker.test.ts` 里过了结构化克隆。
- 主线程上的就地改只读过代码，没有冻住跑过。
- 撤销的内存是按字数估的，没有量堆。

## 逐位相同

- 与旧提交比摘要：同一份 `bench.ts --hash`（1.2 万格）带库、不带库，全世界的摘要在 `b22cd29` 与这一轮逐字节相同。
- `core/content-share.test.ts`：撤销、重做每一步的小数据逐字节、摘要逐项回到当时；改内容再撤销还是原来的对象；中间撤销、重做过的世界与从头重放相同；“没有变化”照旧；做不了的命令回到执行前；检查点克隆以后内容还是共用，恢复后撤销相同；预览的差别补上以后逐字节相同。
- 同一文件的“新旧逐位相同”：旧写法原样抄一份（标着不要改），在七种样子的小数据（内容在中间、最后、挪了位置、没有、空的、`undefined`、种类里有 `undefined`）与十几种改法（深拷贝、换先后、少一种、少一项、改一个字、项里键换先后）的两两组合上比副本、恢复、克隆、比较；一串命令上比 `changed`、移出、新加。
- `src/content-post.test.ts`、`src/worker.test.ts`：过一遍结构化克隆，补上之后逐字节相同；对不上时要完整的；换了 Worker 不串。
